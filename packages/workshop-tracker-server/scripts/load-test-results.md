# Load test results

Generated by `pnpm --filter workshop-tracker-server load-test`
(`scripts/load-test.ts`) — re-run it to refresh these numbers whenever a
change touches the broadcast path in `src/server.ts` (plan 030's own
"Maintenance notes": this script is the initiative's regression guard
against future latency regressions, don't assume the numbers still hold
after such a change without re-running it).

Each run below spins up a fresh, self-contained `workshop-tracker-server`
instance in-process (own ephemeral port, own generated room/presenter
codes), ramps up N simulated participants, measures slide-change and
step-status propagation, then runs the auth-under-load checks (Step 3)
against that same connection count before tearing everything down. The
script overwrites `scripts/load-test-results.md` with the _last_ run's
numbers by default; this file was assembled from two separate runs (50 and
100 participants, PRD §3/§12's stated target range) to keep both on record
at once — see the individual command lines below to reproduce either.

**Caveat on these specific numbers**: this environment's server and
simulated participants all run in the same Node process on `localhost` —
there is effectively zero network latency between them, so these numbers
measure the server's own broadcast-path CPU/event-loop overhead in
isolation, not real workshop-room wifi conditions. That's still the
question this plan needs answered (PRD §12's ~1s target is a _total_
budget, and the server-side broadcast fan-out is the one part of that
budget this codebase controls) — real network latency is additive on top
of these numbers, not a replacement for them.

## Reading these numbers

Both measurements stay under **~11ms** even at 100 concurrent participants —
roughly 90x headroom under the PRD's ~1s target. The room-scoped broadcast
design from plan 027 (dashboard updates only go to sockets that explicitly
joined the `dashboard` Socket.io room, not to every connected client) is
doing its job: `state:update` payload size/frequency was flagged as a risk
in plan 027's own STOP conditions, and this run confirms it isn't a
bottleneck at the PRD's target scale. The auth gate (`auth.ts`'s
constant-time comparison, checked per-event in `server.ts`) also shows no
concurrency-dependent hole — the three rejection checks re-run correctly
with 50 and 100 other participants concurrently connected, matching a
single-connection manual test's behavior exactly.
